
# 1-3. 속성(Attribute)

## 1. 속성의 개념

> **속성(Attribute)** 이란 엔터티를 구체적으로 설명하는 정보로, **업무상 의미를 가지며 더 이상 분리하지 않는 최소 데이터 단위**이다.

- 하나의 엔터티는 자신을 설명하는 여러 **속성**으로 구성된다.
- 예: **'학생' 엔터티** → **'학번'**, **'학생명'**, **'학과'**
- 속성은 해당 업무에서 **관리할 필요가 있는 정보**여야 한다.

### 1.1 엔터티 · 인스턴스 · 속성 · 속성값

다음은 **'학생' 엔터티**를 표로 표현한 예시이다.

| **학번** | **학생명** | **학과** |
|:---:|:---:|:---:|
| **20251001** | **홍길동** | **컴퓨터공학과** |
| 20251002 | 이영희 | 경영학과 |

| 구분 | 표에서 의미하는 것 | 예시 |
|---|---|---|
| **엔터티(Entity)** | 관리 대상인 **표 전체의 개념** | '학생' |
| **인스턴스(Instance)** | 특정 학생을 나타내는 **한 행** | 학번이 '20251001'인 학생 |
| **속성(Attribute)** | 학생의 특성을 나타내는 **열** | '학번', '학생명', '학과' |
| **속성값(Attribute Value)** | 한 인스턴스의 특정 속성에 저장된 **값** | '홍길동', '컴퓨터공학과' |

**핵심 관계(SQLD 기본 원칙)**

1. 하나의 **엔터티**는 **2개 이상의 인스턴스**를 가진다.
2. 하나의 **엔터티**는 **2개 이상의 속성**을 가진다.
3. 하나의 **인스턴스**에서 하나의 **속성**은 원칙적으로 **하나의 속성값**을 가진다.

> **주의:** 위의 '2개 이상'은 SQLD에서 학습하는 기본적인 모델링 원칙이다. 실제 설계 상황에 따라 데이터가 아직 1건이거나 속성이 적을 수도 있으므로, 데이터베이스의 물리적 제약조건과 혼동하지 않는다.

### 1.2 단일값 속성과 다중값 속성

| 구분 | 의미 | 예시 |
|---|---|---|
| **단일값 속성** | 하나의 인스턴스가 해당 속성에 **한 개의 값**을 가짐 | 학생의 '학번' |
| **다중값 속성** | 하나의 인스턴스에 해당하는 **여러 값**이 존재할 수 있음 | 학생의 '연락처'가 여러 개일 때 |

## 2. 좋은 속성의 조건

좋은 속성은 **업무와 직접 관련**이 있고 해당 엔터티를 설명하는 데 필요한 정보로 구성해야 한다.

**예: 학사 관리 업무의 '학생' 엔터티**

| 구분 | 속성 예시 | 판단 이유 |
|---|---|---|
| **포함할 속성** | '학번', '학생명', '학과' | 학사 관리 업무에서 학생을 식별하고 관리하는 데 필요 |
| **일반적으로 제외할 속성** | '좋아하는 음식', 'MBTI' | 일반적인 학사 관리 업무와 직접적인 관련이 낮음 |

> **기억:** 속성의 필요성은 **업무 목적에 따라 달라진다.** 다른 서비스에서는 'MBTI'도 관리 대상 속성이 될 수 있다.

## 3. 속성의 분류

속성은 **출처·성격**에 따른 분류와 **엔터티 안에서의 역할**에 따른 분류로 나눠서 이해한다.

### 3.1 특성에 따른 분류

| 분류 | 의미 | 예시 |
|---|---|---|
| **기본 속성** | 업무 분석을 통해 자연스럽게 도출되는 속성 | '고객명', '생년월일' |
| **설계 속성** | 원래 업무 정보에 없지만 **식별·관리 목적**으로 인위적으로 만든 속성 | '고객번호', '상품코드' |
| **파생 속성** | 다른 속성의 값을 **계산하거나 변형**하여 얻은 속성 | '주문총액' = '주문수량' × '단가' |

**구분 포인트**

- **기본:** 원래 업무에 존재하는 정보
- **설계:** 모델링 과정에서 만들어 낸 정보
- **파생:** 기존 값으로부터 계산한 정보

> **시험 포인트:** '주문총액'처럼 다른 속성으로 계산할 수 있는 값은 **파생 속성**이다. 파생 속성은 계산 결과를 별도로 저장할 경우 원본 값과의 **불일치**에 주의해야 한다.

### 3.2 구성 방식에 따른 분류

| 분류 | 역할 | 예시 |
|---|---|---|
| **PK 속성** (Primary Key) | 각 인스턴스를 **유일하게 식별**하는 기본키 | '학생'의 '학번' |
| **FK 속성** (Foreign Key) | 다른 테이블의 **키를 참조**하여 관계를 연결 | '학생'의 '학과코드' |
| **일반 속성** | PK·FK 역할이 아닌 설명용 속성 | '학생명', '학과명' |

**PK와 FK를 표로 이해하기**

**'학생' 테이블**

| **학번 (PK)** | 학생명 | **학과코드 (FK)** |
|---|---|---|
| 20251001 | 홍길동 | CS |
| 20251002 | 이영희 | BA |

**'학과' 테이블**

| **학과코드 (PK)** | 학과명 |
|---|---|
| CS | 컴퓨터공학과 |
| BA | 경영학과 |

- **'학생.학번'**: 학생을 유일하게 구분하는 **PK**
- **'학생.학과코드'**: **'학과.학과코드'** 를 참조하는 **FK**
- **'학생.학생명'**, **'학과.학과명'**: 대상을 설명하는 **일반 속성**

> **참고:** PK와 FK는 역할이므로 **복합키** 설계에서는 하나의 속성이 PK의 일부이면서 동시에 FK일 수도 있다.

## 4. 도메인(Domain)

> **도메인(Domain)** 이란 하나의 속성이 가질 수 있는 **유효한 값의 범위와 규칙**을 뜻한다.

도메인을 정의하면 **잘못된 형식이나 허용되지 않은 값**이 저장되는 것을 방지할 수 있다.

| 항목 | 설명 | 예시 |
|---|---|---|
| **데이터 타입** | 저장할 값의 종류 | 숫자, 문자, 날짜 |
| **크기** | 문자열 길이·숫자 자릿수 등의 제한 | '학생명' 최대 30자 |
| **허용값·범위** | 입력 가능한 값의 조건 | '학년'은 1~4, '가격'은 0 이상 |
| **NULL 허용 여부** | 값의 누락을 허용할지 결정 | '학번'은 **NOT NULL** |
| **기본값(Default)** | 값을 생략했을 때 대신 사용할 값 | '학년'의 기본값은 1 |

- **CHECK**: 값이 지정된 조건을 만족하는지 검사하는 제약조건
- **NOT NULL**: 값이 비어 있지 않도록 제한하는 제약조건
- **DEFAULT**: 입력값이 생략되었을 때 적용할 기본값 설정

> **구분:** **도메인**은 속성의 유효한 값 범위에 관한 개념이다. **DEFAULT** 는 관련된 열 정의·입력 규칙이지만, 그 자체로 모든 입력값의 유효성을 제한하는 조건은 아니다.

## 5. 핵심 암기 정리

| 구분 | 핵심 키워드 |
|---|---|
| **속성** | 엔터티를 설명하는 **최소 데이터 단위** |
| **속성값** | 인스턴스의 특정 속성이 가지는 **실제 값** |
| **속성의 특성별 분류** | **기본 / 설계 / 파생** |
| **속성의 구성별 분류** | **PK / FK / 일반** |
| **도메인** | 속성이 가질 수 있는 **유효한 값의 범위·규칙** |

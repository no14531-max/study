
# 2-5. 본질식별자와 인조식별자

## 1. 본질식별자와 인조식별자의 개념

엔터티의 기본키를 선정하는 방식은 **키가 업무적으로 의미를 갖는지**에 따라 두 가지로 구분된다.

- **본질식별자(Natural Identifier):** 업무 과정에서 자연스럽게 발생하는, 데이터 자체의 의미를 가진 식별자
- **인조식별자(Surrogate Identifier):** 본질식별자가 복잡하거나 관리하기 어려울 때, 데이터 식별만을 위해 인위적으로 생성한 식별자

### 1.1 본질식별자와 인조식별자 비교

| 구분 | 본질식별자 | 인조식별자 |
|---|---|---|
| **의미** | 키 자체에 업무적 의미가 있음 | 데이터 식별을 위한 별도의 값 |
| **생성** | 업무적으로 원래 존재하는 속성 활용 | 시스템에서 인위적으로 생성 |
| **장점** | 키만으로도 업무적 의미 파악 가능 | 키가 단순하고 관리가 편리함 |
| **단점** | 키가 복잡하거나 변경될 가능성 | 키 자체로는 업무적 의미 파악 불가 |

---

## 2. 본질식별자와 인조식별자의 적용

### 2.1 본질식별자 사용

**예시: 주문 엔터티**

| **주문일자(PK)** | **회원번호(PK)** | **순번(PK)** | 주문상태 |
|---|---|---|---|
| 2024-02-14 | 001 | 1 | 결제완료 |
| 2024-02-14 | 001 | 2 | 배송중 |

- **'주문일자 + 회원번호 + 순번'** 을 복합식별자로 사용
- 키 자체에 **언제, 누가 주문했는지** 등의 업무적 의미가 포함됨
- 여러 속성을 조합해야 하므로 **키가 길고 관리가 복잡**할 수 있음

### 2.2 인조식별자 사용

본질식별자가 복잡하여 별도의 **'주문번호'** 를 생성한 경우이다.

| **주문번호(PK)** | 주문일자 | 회원번호 | 순번 | 주문상태 |
|---|---|---|---|---|
| 1001 | 2024-02-14 | 001 | 1 | 결제완료 |
| 1002 | 2024-02-14 | 001 | 2 | 배송중 |

- **'주문번호'** 라는 단일 속성으로 데이터를 식별
- 기본키가 단순해져 **다른 테이블과의 관계 설정 및 유지보수에 유리**
- 주문번호 자체에는 **업무적 의미가 없음**

> **주의:** 인조식별자를 사용할 때는 기존 본질식별자의 **업무적 유일성**도 유지해야 한다.
>
> 예를 들어 '주문일자 + 회원번호 + 순번'의 중복을 허용하지 않아야 한다면, 인조식별자와 별개로 **UNIQUE 제약조건** 등을 설정해야 한다.

---

## 3. 식별자 선택 기준

본질식별자와 인조식별자 중 **무조건 우수한 식별자는 없다.**

| 본질식별자 고려 | 인조식별자 고려 |
|---|---|
| 키의 **업무적 의미**가 중요할 때 | 본질식별자가 **길거나 복잡**할 때 |
| 키를 구성하는 속성의 수가 적을 때 | 본질식별자의 **변경 가능성**이 높을 때 |
| 키의 값이 안정적으로 유지될 때 | **개발 편의성과 모델의 유연성**이 중요할 때 |

---

## 4. 핵심 암기 정리

- **본질식별자:** 업무적 의미가 있는 식별자
- **인조식별자:** 식별을 위해 인위적으로 만든 식별자
- **본질식별자 장점:** 업무적 의미 파악 가능
- **인조식별자 장점:** 단순한 키 구성 및 관리 용이
- **인조식별자 주의점:** 기존 업무 식별 속성의 중복을 막는 **별도 제약조건** 필요

> **시험 포인트**
>
> 인조식별자를 사용하더라도 **업무적으로 중복되면 안 되는 속성 조합에 대한 유일성 보장**이 필요하다.
>
> 식별자는 **업무 특성과 데이터 모델의 요구사항**을 고려하여 선택해야 한다.
